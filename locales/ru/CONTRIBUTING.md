# Участие в Zoo Code

Zoo Code — проект сообщества. Мы ценим каждый вклад. Мы работаем по принципу [«сначала задача»](#issue-first-approach). Каждый [Pull Request (PR)](#submitting-a-pull-request) должен ссылаться на задачу в GitHub. Внимательно прочитай это руководство.

## Перед началом

<a id="1-code-of-conduct"></a>

### 1. Кодекс поведения

Все участники должны соблюдать наш [Кодекс поведения](./CODE_OF_CONDUCT.md).

<a id="2-project-roadmap"></a>

### 2. План развития проекта

Наш план показывает направление развития проекта. Согласуй свои изменения с этими целями:

<a id="reliability-first"></a>

### Надёжность прежде всего

- Сделай редактирование через diff и выполнение команд надёжными при каждом запуске.
- Устрани проблемы, которые мешают пользоваться Zoo Code каждый день.
- Сделай Zoo Code работоспособным для всех локалей и платформ.
- Добавь поддержку других поставщиков ИИ и моделей.

<a id="enhanced-user-experience"></a>

### Улучшение удобства использования

- Сделай UI и UX понятными и удобными.
- Улучшай рабочий процесс. Разработчики ждут высокого качества от инструментов, которыми пользуются каждый день.

<a id="leading-on-agent-performance"></a>

### Лидерство в производительности агентов

- Создай оценочные тесты (evals), которые измеряют продуктивность в реальных условиях.
- Сделай evals простыми для запуска и чтения.
- Выпускай улучшения, которые заметно повышают результаты evals.

В PR укажи, какие из этих направлений поддерживает изменение.

<a id="3-join-the-zoo-code-community"></a>

### 3. Присоединяйся к сообществу Zoo Code

- **Discord:** Присоединяйся к нашему [Discord](https://discord.gg/VxfP4Vx3gX).
- **Reddit:** Присоединяйся к нашему [Reddit](https://www.reddit.com/r/ZooCode/).

## Поиск и планирование работы

<a id="types-of-contributions"></a>

### Виды участия

- **Исправление ошибок:** Исправляй проблемы в коде.
- **Новые функции:** Добавляй возможности.
- **Документация:** Улучшай руководства и делай их понятнее.

<a id="issue-first-approach"></a>

### Принцип «сначала задача»

Любая работа начинается с задачи в GitHub. Используй наши короткие шаблоны.

- **Проверь существующие задачи:** Выполни поиск в [GitHub Issues](https://github.com/Zoo-Code-Org/Zoo-Code/issues).
- **Создай задачу** с помощью:
    - **Улучшения:** Шаблон "Enhancement Request" (простой текст с акцентом на пользу для пользователя).
    - **Ошибки:** Шаблон "Bug Report" (минимальный пример воспроизведения, ожидаемый и фактический результат, версия).
- **Напиши задачу** по правилам раздела [«Стиль текста»](#writing-style) ниже.
- **Хочешь взяться за задачу?** Оставь комментарий "Claiming" в задаче. Затем свяжись с основной командой в [Discord](https://discord.gg/VxfP4Vx3gX), чтобы тебя назначили исполнителем. Основная команда подтвердит назначение в обсуждении.
- **PR должен ссылаться на задачу.** Мы можем закрыть PR без ссылки.

<a id="deciding-what-to-work-on"></a>

### Выбор работы

- Посмотри [страницу GitHub Issues](https://github.com/Zoo-Code-Org/Zoo-Code/issues).
- Для работы с документацией перейди в [Zoo Code Docs](https://github.com/Zoo-Code-Org/Zoo-Code-Docs).

<a id="reporting-bugs"></a>

### Сообщения об ошибках

- Сначала проверь существующие сообщения.
- Создай новую задачу с [шаблоном "Bug Report"](https://github.com/Zoo-Code-Org/Zoo-Code/issues/new/choose) и укажи:
    - Понятные пронумерованные шаги для воспроизведения
    - Ожидаемый и фактический результат
    - Версию Zoo Code (обязательно)
    - Поставщика API и модель, если они важны
- **Проблемы безопасности:** Сообщай о них непублично через [security advisories](https://github.com/Zoo-Code-Org/Zoo-Code/security/advisories/new).

<a id="development--submission-process"></a>

## Разработка и отправка изменений

<a id="development-setup"></a>

### Настройка среды разработки

1. **Создай форк и клонируй репозиторий:**

```
git clone https://github.com/YOUR_USERNAME/Zoo-Code.git
```

2. **Установи зависимости:**

```
pnpm install
```

3. **Отладка:** Открой проект в VS Code (`F5`).

<a id="writing-code-guidelines"></a>

### Правила работы с кодом

- Один PR для одной функции или исправления.
- Соблюдай лучшие практики ESLint и TypeScript.
- Пиши понятные, содержательные сообщения коммитов со ссылками на задачи (например, `Fixes #123`). Соблюдай [правила стиля](#writing-style).
- Полностью протестируй изменение (`npm test`).
- Перед отправкой выполни rebase на последнюю версию ветки `main`.

<a id="submitting-a-pull-request"></a>

### Отправка Pull Request

- Начни с **Draft PR**, если хочешь получить ранние отзывы.
- Опиши изменения с помощью Pull Request Template. Соблюдай [правила стиля](#writing-style).
- Укажи задачу в описании или заголовке PR (например, "Fixes #123").
- Для изменений UI добавь снимки экрана или видео.
- Укажи, нужно ли обновить документацию.

<a id="pull-request-policy"></a>

### Политика Pull Request

- PR должен ссылаться на задачу GitHub с назначенным исполнителем. Для назначения оставь комментарий "Claiming" в задаче. Затем свяжись с основной командой в [Discord](https://discord.gg/VxfP4Vx3gX). Основная команда подтвердит назначение в обсуждении.
- Мы можем закрыть PR без ссылки.
- PR должен пройти тесты CI, соответствовать плану развития и иметь понятную документацию.

<a id="review-process"></a>

### Процесс проверки

PR, готовый к проверке, должен соответствовать этим условиям:

- Он проходит обязательные проверки CI.
- Он учитывает замечания проверки, которые требуют действий.
- Он получает новое одобрение сопровождающего или CODEOWNER. Это происходит после автоматической проверки последнего коммита.

Автоматическая проверка может добавить комментарий с указаниями и управляемые метки состояния. Выполни следующий шаг из комментария. Не меняй метки самостоятельно. Новые коммиты сбрасывают состояние проверки изменённого кода.

Метка `community-approved` показывает новое одобрение сообщества для последнего коммита. После этого PR ждёт проверки сопровождающего. Метка помогает сопровождающим выбрать приоритет. Она не заменяет проверку сопровождающего или обязательную проверку. Меткой управляет процесс проверки.

Автоматическая проверка помогает сопровождающим. Она не заменяет одобрение человека. Внешние участники не могут управлять CodeRabbit через комментарии. Подходящая проверка запускается повторно сама после прохождения обязательного CI. Исключительные повторные запуски выполняют сопровождающие. Предупреждения носят рекомендательный характер, если политика репозитория не говорит обратного. Встроенные обязательные проверки GitHub, правила CODEOWNER и защита проверки определяют, можно ли объединить PR.

- **Ежедневный разбор:** Сопровождающие выполняют быстрые проверки.
- **Еженедельная подробная проверка:** Сопровождающие проводят полную оценку.
- **Быстро вноси доработки**, когда получаешь отзывы.

<a id="pull-request-expectations"></a>

### Требования к Pull Request

PR должен быть протестирован, удобен для проверки и поддержки. Перед открытием PR проверь следующее:

- Изменение решает одну конкретную задачу, ошибку или улучшение.
- Ты можешь объяснить, что делает изменение и почему оно верно.
- Ты протестировал изменение на своём компьютере, насколько это возможно.
- Ты ответишь на замечания и внесёшь разумные доработки.
- Перед объединением сопровождающим не нужно переписывать или перепроектировать изменение либо брать его поддержку на себя.

Сопровождающие могут закрыть PR по следующим причинам:

- Он не завершён.
- Он слишком объёмный.
- В нём нет активности.
- Он не соответствует направлению проекта.
- Он создаёт слишком много работы по проверке или поддержке.

Закрытие PR не является оценкой участника. Это означает, что сопровождающие не могут принять изменение в текущем виде.

Бот также закрывает PR автоматически:

- **60 дней без активности:** Бот помечает PR как устаревший после 60 дней без активности. Если ещё 7 дней нет активности, бот закрывает PR. Новый комментарий, коммит или проверка сбрасывает таймер.
- **14 дней без активности автора:** Когда проверяющий запрашивает изменения, бот добавляет метку `awaiting-author`. Активность автора сбрасывает таймер. Когда изменения готовы, попроси проверяющего проверить их снова.

Чтобы избежать автоматического закрытия PR, добавь метку `do-not-close`, `pinned` или `work-in-progress`.

<a id="ai-assisted-contributions"></a>

### Работа с помощью ИИ

Ты можешь пользоваться инструментами ИИ. Ты по-прежнему полностью отвечаешь за отправленные изменения.

Если ты используешь ИИ для создания PR, ты должен:

- Проверить и понять каждое важное изменение.
- Объяснить реализацию и компромиссы своими словами.
- Самостоятельно протестировать изменение. Если не можешь проверить его в своей среде, объясни причину в описании PR. Также опиши, как проверяющие могут проверить изменение.
- Убедиться, что сгенерированный код верен, необходим и совместим с лицензией проекта.
- Подумать, стоит ли рассказать о помощи ИИ в описании PR. Сделай это, если ИИ существенно повлиял на код, тесты или дизайн. Это поможет проверяющим дать более полезные отзывы.

Не отправляй сгенерированные ИИ изменения, которых ты не понимаешь. Не отправляй изменения, которые не можешь поддерживать во время проверки. Сопровождающие могут закрыть PR, в котором заметна значительная помощь ИИ. Причиной может быть отсутствие проверки человеком, ясного обоснования или доработок по замечаниям.

<a id="writing-style"></a>

### Стиль текста

Эти правила относятся только к текстам на английском языке. Пиши заголовки и тексты задач, заголовки и описания PR, а также сообщения коммитов на [Simplified Technical English (ASD-STE100)](https://www.asd-ste100.org/). Шаблоны задач и PR содержат такое же напоминание.

- Пиши короткими предложениями. В инструкции используй не больше 20 слов.
- Используй простые слова. Пиши "use", а не "utilize". Пиши "start", а не "commence".
- Используй активный залог. Пиши "the parser reads the file", а не "the file is read by the parser".
- Выражай одну мысль в каждом предложении.
- Не используй сокращённые формы, точки с запятой или длинные тире.
- Делай заголовок коротким и конкретным.
- Не меняй точные логи, сообщения об ошибках, идентификаторы, команды или материалы воспроизведения. Вставляй их как есть.

Эти правила помогают писать тексты. Проверяющие не проверяют формальное соответствие ASD-STE100. Код, идентификаторы и синтаксис команд не подпадают под это правило.

<a id="legal"></a>

## Правовые условия

Участвуя в проекте, ты соглашаешься, что твои изменения распространяются по лицензии Apache 2.0. Это лицензия Zoo Code.
