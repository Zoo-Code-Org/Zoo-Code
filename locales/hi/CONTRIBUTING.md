## योगदान देने से पहले

<a id="1-code-of-conduct"></a>

### 1. आचार संहिता

सभी योगदानकर्ताओं को हमारी [आचार संहिता](./CODE_OF_CONDUCT.md) का पालन करना होगा।

<a id="2-project-roadmap"></a>

### 2. परियोजना का रोडमैप

हमारा रोडमैप परियोजना की दिशा दिखाता है। अपने योगदान को इन लक्ष्यों के अनुरूप रखो:

<a id="reliability-first"></a>

### भरोसेमंद काम सबसे पहले

- diff से संपादन और कमांड चलाने को हर बार भरोसेमंद बनाओ।
- उन समस्याओं को हटाओ जो लोगों को रोज़ Zoo Code इस्तेमाल करने से रोकती हैं।
- Zoo Code को सभी भाषाओं और प्लेटफ़ॉर्म पर काम करने लायक बनाओ।
- अधिक AI प्रदाताओं और मॉडलों के लिए समर्थन जोड़ो।

<a id="enhanced-user-experience"></a>

### बेहतर उपयोगकर्ता अनुभव

- UI और UX को स्पष्ट और इस्तेमाल करने में आसान बनाओ।
- काम करने के तरीके को सुधारो। डेवलपर रोज़ इस्तेमाल होने वाले टूल से अच्छे स्तर की उम्मीद रखते हैं।

<a id="leading-on-agent-performance"></a>

### एजेंट के प्रदर्शन में आगे रहना

- मूल्यांकन बेंचमार्क (evals) बनाओ जो वास्तविक काम में उत्पादकता मापें।
- evals को चलाना और पढ़ना आसान बनाओ।
- ऐसे सुधार जारी करो जो evals के स्कोर को स्पष्ट रूप से बढ़ाएँ।

अपने PR में बताओ कि बदलाव इनमें से किन क्षेत्रों में मदद करता है।

<a id="3-join-the-zoo-code-community"></a>

### 3. Zoo Code समुदाय से जुड़ो

- **Discord:** हमारे [Discord](https://discord.gg/VxfP4Vx3gX) से जुड़ो।
- **Reddit:** हमारे [Reddit](https://www.reddit.com/r/ZooCode/) से जुड़ो।

<a id="finding--planning-your-contribution"></a>

## अपना योगदान चुनना और योजना बनाना

<a id="types-of-contributions"></a>

### योगदान के प्रकार

- **बग ठीक करना:** कोड की समस्याएँ ठीक करो।
- **नई सुविधाएँ:** नए फ़ंक्शन जोड़ो।
- **दस्तावेज़:** गाइड सुधारो और उन्हें अधिक स्पष्ट बनाओ।

<a id="issue-first-approach"></a>

### पहले issue

हर योगदान एक GitHub issue से शुरू होता है। हमारे छोटे टेम्पलेट इस्तेमाल करो।

- **मौजूदा issue जाँचो**: [GitHub Issues](https://github.com/Zoo-Code-Org/Zoo-Code/issues) में खोजो।
- **एक issue बनाओ** और इस्तेमाल करो:
    - **सुधार:** "Enhancement Request" टेम्पलेट (सरल भाषा, उपयोगकर्ता के लाभ पर ध्यान)।
    - **बग:** "Bug Report" टेम्पलेट (बग दोहराने का न्यूनतम उदाहरण, अपेक्षित और वास्तविक परिणाम, संस्करण)।
- **issue लिखते समय** नीचे दी गई [लिखने की शैली](#writing-style) का पालन करो।
- **इस पर काम करना चाहते हो?** issue पर "Claiming" टिप्पणी करो। फिर [Discord](https://discord.gg/VxfP4Vx3gX) पर मुख्य टीम से संपर्क करो ताकि वह तुम्हें issue सौंपे। मुख्य टीम थ्रेड में इसकी पुष्टि करती है।
- **PR में issue का लिंक होना चाहिए।** हम बिना लिंक वाले PR बंद कर सकते हैं।

<a id="deciding-what-to-work-on"></a>

### किस पर काम करना है, यह तय करना

- [GitHub Issues पेज](https://github.com/Zoo-Code-Org/Zoo-Code/issues) देखो।
- दस्तावेज़ों के लिए [Zoo Code Docs](https://github.com/Zoo-Code-Org/Zoo-Code-Docs) पर जाओ।

<a id="reporting-bugs"></a>

### बग की रिपोर्ट करना

- पहले मौजूदा रिपोर्ट जाँचो।
- ["Bug Report" टेम्पलेट](https://github.com/Zoo-Code-Org/Zoo-Code/issues/new/choose) से नई बग रिपोर्ट बनाओ और ये बातें जोड़ो:
    - बग दोहराने के स्पष्ट, क्रमांकित चरण
    - अपेक्षित परिणाम और वास्तविक परिणाम
    - Zoo Code का संस्करण (ज़रूरी)
    - API प्रदाता और मॉडल, अगर वे मायने रखते हैं
- **सुरक्षा समस्याएँ**: [सुरक्षा सलाह](https://github.com/Zoo-Code-Org/Zoo-Code/security/advisories/new) के माध्यम से निजी तौर पर रिपोर्ट करो।

<a id="development--submission-process"></a>

## विकास और बदलाव भेजने की प्रक्रिया

<a id="development-setup"></a>

### विकास का सेटअप

1. **Fork और clone करो:**

```
git clone https://github.com/YOUR_USERNAME/Zoo-Code.git
```

2. **निर्भरताएँ इंस्टॉल करो:**

```
pnpm install
```

3. **डीबगिंग:** VS Code से खोलो (`F5`)।

<a id="writing-code-guidelines"></a>

### कोड लिखने के निर्देश

- हर सुविधा या सुधार के लिए एक केंद्रित PR बनाओ।
- ESLint और TypeScript के अच्छे तरीकों का पालन करो।
- स्पष्ट और वर्णनात्मक commit लिखो जिनमें issue का संदर्भ हो (उदाहरण के लिए, `Fixes #123`)। [लिखने की शैली](#writing-style) का पालन करो।
- अपने बदलाव को पूरी तरह जाँचो (`npm test`)।
- भेजने से पहले नवीनतम `main` शाखा पर rebase करो।

<a id="submitting-a-pull-request"></a>

### Pull Request भेजना

- जल्दी प्रतिक्रिया चाहते हो तो **ड्राफ़्ट PR** से शुरू करो।
- Pull Request Template से अपने बदलावों का वर्णन करो। [लिखने की शैली](#writing-style) का पालन करो।
- PR के विवरण या शीर्षक में issue का लिंक जोड़ो (उदाहरण के लिए, "Fixes #123")।
- UI के बदलावों के लिए स्क्रीनशॉट या वीडियो जोड़ो।
- बताओ कि बदलाव के लिए दस्तावेज़ों को अपडेट करना ज़रूरी है या नहीं।

<a id="pull-request-policy"></a>

### Pull Request नीति

- PR में सौंपे गए GitHub issue का संदर्भ होना चाहिए। issue सौंपने के लिए उस पर "Claiming" टिप्पणी करो। फिर [Discord](https://discord.gg/VxfP4Vx3gX) पर मुख्य टीम से संपर्क करो। मुख्य टीम थ्रेड में इसकी पुष्टि करती है।
- हम बिना लिंक वाले PR बंद कर सकते हैं।
- PR को CI परीक्षण पास करने चाहिए, रोडमैप का पालन करना चाहिए और उसके दस्तावेज़ स्पष्ट होने चाहिए।

<a id="review-process"></a>

### समीक्षा प्रक्रिया

समीक्षा के लिए तैयार PR को ये शर्तें पूरी करनी होंगी:

- वह ज़रूरी CI जाँच पास करता है।
- वह समीक्षा की उन टिप्पणियों पर काम करता है जिनमें कार्रवाई चाहिए।
- उसे रखरखावकर्ता या CODEOWNER से नई मंज़ूरी मिलती है। यह नवीनतम commit की स्वचालित समीक्षा पूरी होने के बाद होता है।

स्वचालित समीक्षा निर्देश वाली टिप्पणी और प्रबंधित स्थिति लेबल जोड़ सकती है। टिप्पणी में बताए अगले चरण का पालन करो। लेबल खुद मत बदलो। नए commit बदले हुए कोड की समीक्षा स्थिति रीसेट करते हैं।

`community-approved` लेबल नवीनतम commit पर समुदाय की नई मंज़ूरी दिखाता है। फिर PR रखरखावकर्ता की समीक्षा का इंतज़ार करता है। यह लेबल रखरखावकर्ताओं को प्राथमिकता का सुझाव देता है। यह रखरखावकर्ता की समीक्षा या ज़रूरी जाँच की जगह नहीं लेता। समीक्षा का कार्यप्रवाह इस लेबल को संभालता है।

स्वचालित समीक्षा रखरखावकर्ताओं की मदद करती है। यह इंसान की मंज़ूरी की जगह नहीं लेती। बाहरी योगदानकर्ता टिप्पणियों से CodeRabbit को निर्देश नहीं दे सकते। शर्तें पूरी करने वाली समीक्षा ज़रूरी CI पास होने के बाद खुद फिर शुरू होती है। रखरखावकर्ता विशेष मामलों में समीक्षा फिर शुरू करवाते हैं। चेतावनियाँ सुझाव हैं, जब तक रिपॉज़िटरी की नीति कुछ और न कहे। GitHub की ज़रूरी जाँच, CODEOWNER नियम और समीक्षा सुरक्षा तय करते हैं कि PR मर्ज हो सकता है या नहीं।

- **रोज़ की छँटाई:** रखरखावकर्ता जल्दी जाँच करते हैं।
- **साप्ताहिक गहन समीक्षा:** रखरखावकर्ता पूरा मूल्यांकन करते हैं।
- **जल्दी सुधार करो** जब तुम्हें प्रतिक्रिया मिले।

<a id="pull-request-expectations"></a>

### Pull Request से अपेक्षाएँ

PR की समीक्षा आसान होनी चाहिए, उसका परीक्षण होना चाहिए और उसका रखरखाव आसान होना चाहिए। PR खोलने से पहले ये बातें जाँचो:

- बदलाव एक खास issue, बग या सुधार से जुड़ा है।
- तुम समझा सकते हो कि बदलाव क्या करता है और सही क्यों है।
- जहाँ संभव था, तुमने अपने कंप्यूटर पर बदलाव जाँचा है।
- तुम समीक्षा की प्रतिक्रिया का जवाब दोगे और ज़रूरी, उचित बदलाव करोगे।
- मर्ज करने से पहले रखरखावकर्ताओं को बदलाव दोबारा लिखने, फिर डिज़ाइन करने या उसकी ज़िम्मेदारी लेने की ज़रूरत नहीं है।

रखरखावकर्ता इन कारणों से PR बंद कर सकते हैं:

- वह अधूरा है।
- उसका दायरा बहुत बड़ा है।
- वह निष्क्रिय है।
- वह परियोजना की दिशा का पालन नहीं करता।
- उससे समीक्षा या रखरखाव का बहुत ज़्यादा काम बढ़ता है।

PR बंद करना योगदानकर्ता पर निर्णय नहीं है। इसका मतलब है कि रखरखावकर्ता बदलाव को उसके मौजूदा रूप में स्वीकार नहीं कर सकते।

एक बॉट भी PR अपने आप बंद करता है:

- **60 दिन की निष्क्रियता:** बॉट 60 दिन बिना गतिविधि के बाद PR को निष्क्रिय चिह्नित करता है। अगले 7 दिन भी कोई गतिविधि न हो तो वह PR बंद करता है। नई टिप्पणी, commit या समीक्षा टाइमर रीसेट करती है।
- **लेखक की 14 दिन की निष्क्रियता:** समीक्षक बदलाव माँगता है तो बॉट `awaiting-author` लेबल जोड़ता है। लेखक की गतिविधि निष्क्रियता का टाइमर रीसेट करती है। बदलाव तैयार हों तो समीक्षक से नई समीक्षा माँगो।

PR को अपने आप बंद होने से रोकने के लिए `do-not-close`, `pinned` या `work-in-progress` लेबल जोड़ो।

<a id="ai-assisted-contributions"></a>

### AI की मदद से योगदान

तुम AI टूल इस्तेमाल कर सकते हो। तुम भेजे गए काम के लिए पूरी तरह ज़िम्मेदार रहते हो।

PR बनाने में AI टूल की मदद लेते हो तो तुम्हें ये काम करने होंगे:

- हर महत्वपूर्ण बदलाव की समीक्षा करो और उसे समझो।
- कार्यान्वयन और उसके फायदे-नुकसान अपने शब्दों में समझाओ।
- बदलाव खुद जाँचो। अपने वातावरण में परीक्षण नहीं कर सकते तो PR के विवरण में कारण बताओ। यह भी बताओ कि समीक्षक बदलाव कैसे जाँच सकते हैं।
- जाँचो कि तैयार किया गया कोड सही, ज़रूरी और परियोजना के लाइसेंस के अनुकूल है।
- PR के विवरण में AI की मदद बताने पर विचार करो। जब AI की मदद ने कोड, परीक्षण या डिज़ाइन को बहुत बदला हो, तो ऐसा करो। इससे समीक्षक बेहतर प्रतिक्रिया दे सकते हैं।

AI से बने ऐसे बदलाव मत भेजो जिन्हें तुम नहीं समझते। ऐसे बदलाव मत भेजो जिनका समीक्षा के दौरान रखरखाव नहीं कर सकते। रखरखावकर्ता ऐसा PR बंद कर सकते हैं जो बहुत अधिक AI की मदद से बना लगता है। वे ऐसा कर सकते हैं अगर उसमें इंसान की जाँच, स्पष्ट कारण या समीक्षा में आगे की भागीदारी न हो।

<a id="writing-style"></a>

### लिखने की शैली

ये नियम अंग्रेज़ी में लिखे पाठ पर लागू होते हैं। issue के शीर्षक और पाठ, PR के शीर्षक और विवरण, और commit संदेश [Simplified Technical English (ASD-STE100)](https://www.asd-ste100.org/) में लिखो। issue और PR के टेम्पलेट भी यही याद दिलाते हैं।

- छोटे वाक्य लिखो। एक निर्देश के लिए 20 या उससे कम शब्द इस्तेमाल करो।
- सरल शब्द इस्तेमाल करो। "utilize" की जगह "use" लिखो। "commence" की जगह "start" लिखो।
- कर्तृवाच्य इस्तेमाल करो। "the file is read by the parser" की जगह "the parser reads the file" लिखो।
- हर वाक्य में एक विचार लिखो।
- संक्षिप्त शब्द रूप, अर्धविराम या लंबे डैश इस्तेमाल मत करो।
- शीर्षक छोटा और स्पष्ट रखो।
- मूल लॉग, त्रुटि संदेश, पहचानकर्ता, कमांड या बग दोहराने के प्रमाण मत बदलो। उन्हें ज्यों का त्यों पेस्ट करो।

ये नियम लिखने के मार्गदर्शन के लिए हैं। समीक्षक ASD-STE100 का औपचारिक अनुपालन नहीं जाँचते। कोड, पहचानकर्ता और कमांड की सिंटैक्स इस नियम में शामिल नहीं हैं।
