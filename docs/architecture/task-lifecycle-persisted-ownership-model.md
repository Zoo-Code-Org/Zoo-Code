# Task lifecycle persisted ownership and generation model

This document is the specification deliverable for the P1 workstream, "Persisted ownership and generation" (tracked by [#1689](https://github.com/Zoo-Code-Org/Zoo-Code/issues/1689) under umbrella [#1688](https://github.com/Zoo-Code-Org/Zoo-Code/issues/1688)). It discharges the documentation/formal-model scope of five remediation blocks, and records one open block, from the [remediation block register](./task-lifecycle-remediation-blocks.md):

- `LIFE-BLK-P1-001` for `LIFE-GAP-001` (stale cross-host completion ownership);
- `LIFE-BLK-P1-002` for `LIFE-GAP-002` (stale message save restoring detached lineage);
- `LIFE-BLK-P1-012` for `LIFE-GAP-012` (attempt/generation identity for completion);
- `LIFE-BLK-P1-017` for `LIFE-GAP-017` (mutable store cache reads);
- `LIFE-BLK-P1-020` for `LIFE-GAP-020` (stale-cache and convergence histories);
- `LIFE-BLK-P1-039` for `LIFE-GAP-039` (continuation of a completed task). This block is open. See its section below.

Like the parent [gap report](./task-lifecycle-gap-report.md), this is a documentation and formal-model artifact. It does not change production behavior, and completing these blocks does not close any parent `LIFE-GAP`: every closure criterion below names production evidence that belongs to a later implementation PR. Where a closure criterion names interruption, stale-write, or recovery evidence, the required tests are deterministic fault-injection tests — interruption at each persistence step with rollback verification — never timing-based sleeps or smoke tests.

**Code references.** Line numbers in this document are at commit `7c291bb08` (`main`, 2026-09-26). Symbol names stay valid after later edits. Line numbers can drift.

## Shared ownership vocabulary

All blocks use one vocabulary, established here so that dependent workstreams (P2 recovery, P7 serial baseline) can reference it without re-deriving it.

- **Authoritative record.** Each task's `history_item.json` file on disk is the authoritative record. Every extension host's `TaskHistoryStore` cache is a replica that may lag disk (stale) and may contain fields no peer has committed.
- **Stale snapshot.** A `HistoryItem` captured from a host cache, or rebuilt from a live `Task`, before a peer host's latest commit. Completion (`ClineProvider.reopenParentFromDelegation`) and message saves (`Task.saveClineMessages`) build writes from stale snapshots by construction: the snapshot is taken outside the per-file disk lock.
- **Lock-time revalidation.** The check executed inside `safeWriteJson`'s merge callback while holding the per-task advisory file lock, implemented by `mergeHistoryDelta` (`src/core/task-persistence/taskStoreConcurrency.ts`). Today it enforces only status-transition legality (`VALID_TASK_STATUS_TRANSITIONS`) plus `childIds` union semantics. It does not check exact-child ownership.
- **Lock-time ownership check.** A required new check on the parent record, specified under LIFE-BLK-P1-001. It runs in the parent file's merge. The gap report's dependency column for `LIFE-GAP-001` calls it the disk-authoritative ownership guard.
- **Lock-time generation check.** A required new check on the child record, specified under LIFE-BLK-P1-012. It runs in the child file's merge. It is a separate check because the generation lives in the child file, and each file has its own lock. `mergeHistoryDelta` sees only one disk record per call, so one check cannot compare both files under their locks.
- **Cached updater input.** Both `TaskHistoryStore.atomicReadAndUpdate` and `atomicUpdatePair` pass the updater the cached item, not the disk record. The updater result becomes a delta against the cache, and `mergeHistoryDelta` merges that delta into disk. So a reducer check inside an updater validates the cache, not disk.
- **Lifecycle-owned fields.** The fields whose authoritative writer is the lifecycle layer: `status`, `rootTaskId`, `parentTaskId`, `delegatedToId`, `childIds`, `awaitingChildId`, `completedByChildId`, `completionResultSummary`, and `pendingAction`. The block-level ownership table is under LIFE-BLK-P1-002 below.
- **Attempt generation.** A monotonically increasing per-task token distinguishing one execution attempt of the same task ID from the next after interruption and resume. No such persisted token exists today; `PendingTaskAction.actionId` is pending-approval identity, not attempt identity (see LIFE-BLK-P1-012).

## LIFE-BLK-P1-001 — lock-time ownership check (GAP-001)

**Bounded property.** In every reachable two-host history, a write that assumes the parent awaits child `c` may change the parent record only while the on-disk parent awaits `c`. Four writes depend on the parent's awaited child: completion (`completeDelegatedChild`), abandonment (`abandonDelegatedChild`), re-delegation (`delegateTaskToChild` on a parent that is already delegated), and first delegation (`delegateTaskToChild` on a parent that awaits no child). A first delegation assumes that the parent awaits no child. Exclusions: crash atomicity of the pair write itself (`LIFE-BLK-P2-004`), more than two hosts, advisory-lock implementation semantics, and power-loss durability.

**Production symbols and ownership boundary.** All four writes build the parent change from cached state (see Cached updater input):

- Completion: `ClineProvider.reopenParentFromDelegation` calls `TaskHistoryStore.atomicUpdatePair` (`ClineProvider.ts:4273`).
- Abandonment: `abandonSubtask` reads `parentHistory` through `getTaskWithId` (`ClineProvider.ts:4437`) and calls `atomicUpdatePair` (`:4468-4473`). `delegated → active` is a legal transition, so a stale abandon passes the status check on disk and clears a newer re-delegation.
- Re-delegation and first delegation: `delegateParentAndOpenChild` calls `atomicReadAndUpdate` (`ClineProvider.ts:3992`), which runs `delegateTaskToChild` (`:4001`). A stale re-delegation keeps the status `delegated`, so no status check runs at all. A first delegation from a stale cache has the same gap. If host B delegates the parent first, host A's cache still shows the parent as `active`. Host A then writes `delegated` over the `delegated` on disk, so the status check is skipped, and host B's `awaitingChildId` is overwritten.

Inside each write, `writeTaskFile` runs `mergeHistoryDelta` under that file's advisory lock. The stale window is the gap between the cached snapshot and the lock-time merge.

**Write order.** `atomicUpdatePair` writes the first record, then the second (`TaskHistoryStore.ts:1040-1043`). Completion and abandonment both pass the child first. If the parent write is rejected, the child write has already landed: the child is completed or detached while the parent still awaits another child. The lock-time generation check runs in the child write, so it can reject before anything commits. The lock-time ownership check runs in the parent write, after the child commit. A check of the parent before the child write narrows this window but does not close it, because the parent lock is released before the child write and a peer can re-delegate in that gap. `LIFE-BLK-P2-004` owns the recovery for this order in every case.

**Recovery rule: roll forward from the child** (see [ADR-0005](./adr/0005-pair-write-roll-forward.md)). The child write is the first commit, and the system never undoes it.

- The parent write is rejected because ownership moved. The child was already superseded, so its committed state is a legal final state. A `completed` child keeps its status and never delivers its result. A detached child stays detached. The parent keeps its newer delegation. The implementation must log a warning that names the child, the parent, and the parent's newer awaited child, so the lost result is visible.
- The parent write fails for another reason, for example an I/O error. The parent then still awaits the child, and the failing host retries the parent write at once through the normal write path, with the lock-time ownership check.
- If the process stops before the retry, startup reconciliation is the backstop. `reconcileDelegationStateCore` already rolls a delegated parent forward from a `completed` awaited child and copies its `completionResultSummary` (`TaskHistoryStore.ts:478-494`). It runs only at startup (`:133`) and after migration (`:827`), not in the periodic `reconcile()`. It writes with `skipTransitionCheck` and has no ownership check.
- One case needs a new rule: a delegated parent whose awaited child no longer links back to it. The new rule releases that parent to `active`. This is a behavior change. Today a parent that awaits an `interrupted` child is left as-is (`TaskHistoryStore.ts:403-407`). The fail-closed cancel detach (`ClineProvider.ts:3638`) produces this case most often, and today it leaves the parent delegated to a child that can never report back.
- An existing two-record repair-intent mechanism, `replayDelegationRepairIntent` (`TaskHistoryStore.ts:127`), runs before startup reconciliation. `LIFE-BLK-P2-004` decides whether the roll-forward writes a repair intent through it.
- The repairs are idempotent, because they read only committed records. `LIFE-BLK-P2-004` owns their implementation and the fault-injection tests.

**Model boundary.** The `revalidate` phase of the shared-store checker (`scripts/check-task-store-concurrency.ts`) is the faithful model of this boundary: it executes the production `mergeHistoryDelta` against current disk state while holding the modeled per-file lock. The checker's `stale completion ownership` scenario drives host A's completion of `child-a` against host B's re-delegation to `child-b`.

- **Lock-time ownership check (named, required).** When a delta comes from one of the four writes above, lock-time revalidation must verify that the disk parent awaits the same child that the snapshot awaited: `disk.parent.awaitingChildId === c` for completion, abandonment, and re-delegation, and, for a first delegation, no awaited child other than the one the snapshot saw. It keeps the recovery-compatible `active` parent carve-out that the production reducer already recognizes, including an `active` parent that still names an `awaitingChildId`, and it rejects the delta otherwise. The generation comparison is not part of this check. The lock-time generation check runs in the child file's merge (LIFE-BLK-P1-012). Today's check verifies only status-transition legality, which is why the witness below exists.
- **Witness (retained).** The checker's `#1469` known-unsafe witness — the exact 14-action shortest trace ending in `complete-a.commit(parent)` after `redelegate-b.commit(parent)` — remains the ratchet. CI fails if the witness's causal order changes or disappears without promotion.
- **Bounds.** Two hosts, three task slots, depth ≤ 32, ≤ 100,000 states, six scenarios; all seven phases and three semantic landmarks must remain reachable. These bounds are unchanged by this block.
- **Production test required for promotion.** A deterministic two-store test (the `TaskHistoryStore.crossInstance.spec.ts` pattern, two real stores on one storage path): store A captures a stale completion snapshot for `child-a`, store B completes the interrupt-and-redelegate sequence to `child-b`, then store A's `atomicUpdatePair` completion attempt must be rejected at lock-time revalidation and must leave B's committed handoff intact (parent still `delegated` to `child-b`, `child-b` active and linked). Three more cases use the same pattern: a stale abandon, a stale re-delegation, and a stale first delegation from store A, each after store B has changed the parent's awaited child. In every case the parent must keep B's committed handoff. The child has two legal outcomes under the roll-forward rule (ADR-0005). If the parent check rejects before the child write, the child is unchanged. If the child write committed first, the child keeps its superseded final state, and the warning is logged. Only after that test exists and passes may the checker witness be promoted to a universal invariant.

**Model/checker change.** None in this PR, by design: encoding the ownership check as a model transition now would specify behavior production does not implement, violating the suite's faithfulness rule. The witness stays a witness until the production guard lands; this block names the boundary, check, bounds, and promotion test so the later implementation PR has an objective target.

## LIFE-BLK-P1-002 — lifecycle-owned fields versus metadata writes (GAP-002)

**Bounded property (monotonic detachment).** Once a detach commit lands — `abandonDelegatedChild` clears the child's `parentTaskId`/`rootTaskId` — no later write whose lineage fields derive from a pre-detach snapshot may reintroduce them. This property is **currently violated in production**; this block makes the invariant and its ownership contract explicit and claims no present safety.

**Field ownership table.** Authoritative-writer assignment for every `historyItemSchema` field (`packages/types/src/history.ts`):

| Field                                                                     | Writers today                                                                                                                                                                                                                                                                                                                                                                                                          | Metadata writers may write?                                                                |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `status`                                                                  | Lifecycle writes. Delegation, completion, and abandonment use the atomic updaters (`ClineProvider.ts:3992, 4273, 4468`). Standalone completion, interrupt, and cancel use `updateTaskHistory`, which calls `upsert` (`:400, 718, 3612`). The fail-closed cancel write at `:3638` also writes `interrupted`, and it clears lineage.. A child's first status comes from `initialStatus: "active"` at creation (`:3973`). | Preserve the current value only. `Task.saveClineMessages` does this (`Task.ts:1411-1412`). |
| `rootTaskId`, `parentTaskId`                                              | Set on the child at creation, from the live `Task` through `taskMetadata` (`taskMetadata.ts:98-114`). Cleared by `abandonDelegatedChild`, and by the fail-closed cancel detach, which writes through `updateTaskHistory` (`ClineProvider.ts:3626-3638`). `delegateTaskToChild` writes parent fields only (`taskLifecycle.ts:48-54`).                                                                                   | **No.** Today every message save rewrites them from live `Task` state.                     |
| `delegatedToId`, `awaitingChildId`                                        | `delegateTaskToChild`, `completeDelegatedChild`, `abandonDelegatedChild`, and the repair paths                                                                                                                                                                                                                                                                                                                         | No                                                                                         |
| `childIds`                                                                | The same reducers. The merge unions concurrent additions.                                                                                                                                                                                                                                                                                                                                                              | No                                                                                         |
| `completedByChildId`, `completionResultSummary`                           | `completeDelegatedChild` and reconciliation repair. Standalone completion writes `status` only.                                                                                                                                                                                                                                                                                                                        | No                                                                                         |
| `pendingAction`                                                           | `setPendingTaskAction` (`ClineProvider.ts:740`), the compare-and-clear settlement (`:752-757`), and the delegation and completion paths                                                                                                                                                                                                                                                                                | No                                                                                         |
| `id`, `number`, `task`                                                    | Creation                                                                                                                                                                                                                                                                                                                                                                                                               | Creation only                                                                              |
| `ts`                                                                      | Metadata. `taskMetadata` sets it from the last relevant message on every save (`taskMetadata.ts:69-73`).                                                                                                                                                                                                                                                                                                               | Yes                                                                                        |
| `tokensIn`, `tokensOut`, `cacheWrites`, `cacheReads`, `totalCost`, `size` | Metadata (`taskMetadata` accounting)                                                                                                                                                                                                                                                                                                                                                                                   | Yes                                                                                        |
| `workspace`, `mode`, `apiConfigName`                                      | Metadata. Mode and profile updates use `updateTaskHistory`.                                                                                                                                                                                                                                                                                                                                                            | Yes                                                                                        |

Administrative repair paths (`reconcileDelegationStateCore`, `repairActiveDelegation`, migration) write lifecycle fields with `skipTransitionCheck: true`; they are lifecycle-owned writes, not metadata writes.

**Current deviation and witness.** `Task.saveClineMessages` rebuilds `rootTaskId`/`parentTaskId` from the live `Task` via `taskMetadata`, preserving only `status` from the store (`Task.ts`: the `existingStatus` spread). `computeHistoryDelta` therefore includes lineage fields whenever the live snapshot diverges from cache, and `mergeHistoryDelta` applies them last-writer-wins. The shared-store checker's `#1021` known-unsafe witness (`stale save detachment`, the exact 11-action shortest trace through `A.refresh` into `stale-save-a.commit(child-a)`) shows a stale save re-attaching abandoned lineage while preserving the newer `interrupted` status. The witness stays ratcheted until the closure criteria below are met.

**Model/checker change.** None in this PR: the field ownership table and monotonic-detachment invariant are the deliverable, and the checker already retains the exact witness. The later implementation PR must not strip lifecycle fields at the `updateTaskHistory` boundary, because the interrupt, cancel, and standalone-completion writes pass through it (see the table). It must do one of these, then promote the witness to a universal invariant:

- Add a new history write inside `createTask` that persists the child's lineage and its first status. `createTask` writes no history today. `initialStatus: "active"` is only an argument (`ClineProvider.ts:3971-3976`), and the first message save persists both that status and the lineage. Then strip lineage fields from every message save (`Task.saveClineMessages` into `taskMetadata`). Stripping without the new creation write would leave new children unlinked.
- Route every lifecycle write through one lifecycle write API first, and then strip lifecycle fields at the metadata boundary.
- Make lock-time revalidation reject stale lineage deltas (tombstone or generation). It depends on the LIFE-BLK-P1-001 vocabulary above, which this document defines.

**Test evidence required for closure (deterministic fault injection).** Interrupt a save at each persistence step of `Task.saveClineMessages` (message write, metadata build, `updateTaskHistory` upsert) with an interleaved abandonment commit, and assert that after every interruption point the detached lineage is never restored and any partial write rolls back or is superseded by the authoritative record.

## LIFE-BLK-P1-012 — attempt-generation state (GAP-012)

**Bounded property.** A completion produced by attempt `g` of a child may be accepted only while the persisted attempt generation of that child is `g`. A delayed pre-interruption completion (generation `g0`) arriving after resume (generation `g1`) must be rejected. A completion from the resumed attempt (`g1`) must be accepted. Exclusions: wall-clock timing, and the raw-to-durable tool-call identity of a replayed action (`LIFE-BLK-P4-038`). This block owns the generation contract, including staged pending-action replay and stale-action settlement (see Pending actions and settlement). The lock-time generation check enforces the comparison across hosts. It runs in the child file's merge, and it rejects a stale completion before the pair writes anything.

**Production symbols and boundary.** `PendingTaskAction.actionId` (`packages/types/src/history.ts`) correlates one pending create/finish approval and is cleared on settlement; it is not an attempt identity and does not survive into the resumed attempt. The interruption, resume, and completion paths are the `interruptDelegatedChild` reducer, webview/API/IPC resume into `resumeTask`/rehydration, and `completeDelegatedChild` via `reopenParentFromDelegation`.

**Specified generation semantics.** One future optional persisted field, `attemptGeneration`, on the child record (lazy optional-field migration per the gap report's planning assumptions; downgrade readers ignore it):

- Delegation (first attempt) establishes generation `g0`.
- Interruption keeps the generation. A completion that is already in flight when the user stops the child can still land before the next resume. This is accepted: once stopped, the instance is aborted and cannot ask again, so only an in-flight completion can arrive in that window.
- Every resume increments the generation, from `g` to `g+1` (see [ADR-0003](./adr/0003-attempt-generation.md)). The increment happens when the resumed attempt starts to act, not when the task opens. `resumeTaskFromHistory` runs as soon as a `Task` is built from history (`Task.ts:699, 1017, 2225`), before the user answers the `resume_task` ask, so the start of that method is too early. The increment has four points:
    - The normal resume: after the `resume_task` ask returns (`Task.ts:2415`), before the task loop starts.
    - A pending-action replay: after the replay's approval (`Task.ts:2596-2598`), before the replay commits.
    - A pending-action replay that is denied or answered with feedback: before `initiateTaskLoop` (`Task.ts:2643`). The `completion_result` feedback branch also reaches this call (`Task.ts:2625-2628`).
    - `resumeAfterDelegation` (`Task.ts:2875`): at its start, because it continues at once.
- No increment writes a `completed` record, so viewing a completed task does not change it (model invariant 6). Opening a task, or viewing it, changes nothing, so another window keeps its running attempt. Every stop and resume cycle still gets a fresh generation.
- Completion carries the producing attempt's generation; reducers and lock-time revalidation accept it only when it equals the persisted generation.
- A record with no `attemptGeneration` is read as `g0`. A completion delivered with no generation is read as `g0`. It is accepted while the record is at `g0`, and it is rejected once the record is at `g1`. This rule covers a late commit from an old attempt, received by an upgraded reader. An old reader does not run the check at all (next bullet). It does not cover a replayed action (see Pending actions and settlement). The first write that needs a generation writes `g0` explicitly.
- A downgrade reader ignores the field, so it cannot enforce the check. The target architecture records this degraded behavior for mixed-version hosts.
- If the interrupt write fails (the `updateTaskHistory` call at `ClineProvider.ts:718` throws, handled at `:725-729`), the record stays `active` at `g0`. A later `g0` completion is then accepted. This is residual exposure: the user interrupted the child, but a late `g0` completion still lands, because the interruption never committed. The cancel path is different. It sets `interrupted` before its write (`ClineProvider.ts:3611-3612`). If that write throws, the fail-closed catch writes the same `interrupted` record with lineage cleared (`:3638`). So the cancel path never leaves the record `active`.

**Pending actions and settlement.** The #1689 audit mapping requires this block to cover staged pending-action replay, persisted attempt identity, bounded retry, and stale-action settlement. #1714 is the witness: a pending `create_subtask` survived an interruption, and each reopen replayed it into a rejected `interrupted → delegated` transition, up to 545 times.

- Staged replay: `resumePendingTaskAction` replays a persisted `pendingAction` on resume (`Task.ts:2393, 2590, 2622`). A replayed action is a request, not a result. The resumed attempt asks for approval again (`Task.ts:2596`) and then calls `reopenParentFromDelegation` (`Task.ts:2610`). The completion it produces therefore carries the current generation, which the resume set, not the generation that staged the action. This also covers an action staged before the upgrade, which has no token. Without this rule, an approved replay of `finish_subtask` could never commit.
- Persisted attempt identity: `attemptGeneration` is the attempt identity. `PendingTaskAction.actionId` stays the approval identity.
- Stale-action settlement: the open PR #1726 settles a rejected `create_subtask` with a disk-authoritative compare-and-clear on the exact `actionId`. It keeps a replacement action with a different ID, completed records, and other action kinds, and it fails closed when the record is gone. A replacement action has a different `actionId`, so a stale settlement cannot clear it. A replay is different: it reuses the staged `actionId` (`Task.ts:2614`). So a settlement by that `actionId` from the old `g0` attempt on another host can clear the replayed action, and the replayed reopen then fails the pending-action match (`ClineProvider.ts:4278`). **Replay settlement rule: settle on `(actionId, generation)`** (see [ADR-0003](./adr/0003-attempt-generation.md)).

- `pendingAction` gains an optional field for the generation of the attempt that owns it. A replay stamps the new generation onto the action at the same point as the increment: after the replay's approval, before the commit.
- The compare-and-clear settles only when both `actionId` and that generation match. The pending-action match in `reopenParentFromDelegation` compares both.
- `actionId` stays `sanitizeToolUseId(toolCallId)` (`NewTaskTool.ts:105`), so the tie to the tool call that `LIFE-GAP-038` relies on is kept. A settlement from an older attempt on another host no longer matches, because every resume raised the generation. So it cannot clear the replayed action.
- An action with no generation field is read as `g0`, like a record with no token.
- Bounded retry: the rejected action must be settled before the parent is restored, so the same rejected replay cannot repeat.

**Acceptance/rejection landmarks.** These must be reachable:

- `resumed-generation-completion-accepted`, in the lifecycle checker: after a resume, a completion from the resumed attempt moves the child to `completed` and the parent to `active`.
- A rejected stale offer, in the lifecycle checker. A rejection leaves the state unchanged, so no state predicate can see it. Require it as a reachable action under the suite's action-reachability rule, not as a state landmark. Give it its own action name, for example `offerCompleteStale(child)`, because the checker keys action reachability by the name before `(` (`check-task-lifecycle.ts:222`).
- A rejected stale completion at lock time, in the shared-store checker. Host A offers a `g0` completion after host B resumed the child, which raised it to `g1`. The parent still awaits the same child, so the lock-time ownership check passes. The lock-time generation check in the child file's merge rejects it. The rejection leaves the state unchanged, so require it as a reachable action with its own name, not as a state landmark.

**Bounded future checker shape.** Two checkers change, because the lifecycle checker has no lock-time phase.

In `scripts/check-task-lifecycle.ts`:

- Model the generation per child as current versus stale, not as a number. Each completion offer is tagged current or stale. A resume marks every earlier offer stale. This keeps the state space finite across repeated stop and resume cycles, which a numeric counter would not.
- `resume(child)`: enabled when the child is `interrupted`. It marks every earlier offer stale. The status stays `interrupted` until completion, as in production: `interrupted → completed` is the only legal move out of `interrupted` (`taskLifecycle.ts:9`). The interrupt action (`check-task-lifecycle.ts:93`) does not change the generation.
- `offerComplete(child, g)`: enabled only where `completeDelegatedChild`'s preconditions hold, that is, the parent awaits the child and the child is not completed. This guard keeps the reducer from throwing inside `transitions()`. A current `g` is accepted. An older `g` is rejected, and the state stays unchanged. A stale offer is a reachable rejected action, not a disabled one, so the rejection landmark is provable.
- `MAX_DEPTH` is 12 today (`check-task-lifecycle.ts:26`). The implementation PR sets the smallest depth that reaches every landmark with no unseen successor, and records it in the checker constants and in this section. The 10,000-state budget and landmark reachability rules apply unchanged.

In `scripts/check-task-store-concurrency.ts`, add one scenario to the `revalidate` phase: host A offers a `g0` completion after host B resumes the child to `g1`, and the child-file merge runs the lock-time generation check.

**Model/checker change.** None in this PR, justified: no persisted generation token exists in `historyItemSchema`, so there is no faithful production boundary to import, and adding generation state to the checker now would model unimplemented behavior — the same reason the lifecycle model page documents this exclusion today. This specification is the dependency input for `LIFE-BLK-P2-006` (completion commit phases) and `LIFE-BLK-P6-009`/`P6-033` (event and resume-ingress contracts).

## LIFE-BLK-P1-017 — immutable store read semantics (GAP-017)

**Bounded property.** A caller cannot alter the cache or disk state of the store through an object it passed in or got back. This covers reads: an object returned by `TaskHistoryStore.get`, `getAll`, or `getByWorkspace`. It also covers writes: on a first insert, `mergeHistoryDelta` returns the caller's own `incoming` object (`taskStoreConcurrency.ts:24-25`), and `upsertCore` caches it (`TaskHistoryStore.ts:252`), so the caller keeps a live reference to a cache entry. Exclusions: consumers of downstream serialized copies (webview and IPC payloads are structured-cloned at the message boundary). `ClineProvider` sets no `onWrite` callback on `main` since #1664. The store still accepts one, and it would receive `getAll()` arrays that hold the live cache objects, not clones.

**Scope.** #1689 names immutable reads across history types. This inventory covers `TaskHistoryStore` only.

**Current behavior.** `get` returns the live cache object by reference; `getAll` and `getByWorkspace` allocate a new array containing those same live objects. The store's own atomic updaters are safe (`atomicReadAndUpdate`/`atomicUpdatePair` pass `structuredClone` snapshots to updaters), but the public read surface is not.

**Direct-caller inventory (exhaustive over `src/`, `packages/`, `apps/` at the authoring commit).** `TaskHistoryStore` is constructed per `ClineProvider` instance (one per extension-host view) and reached as `provider.taskHistoryStore`.

| Caller                                                                                                                                 | Use of returned record                                                                    | Mutates?              |
| -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | --------------------- |
| `ClineProvider` (~25 sites: delegation guards, completion, abandonment, eviction, mode/profile updates, webview/API state, broadcasts) | Reads fields. Every write path spreads into a new object first                            | No                    |
| `ClineProvider.getTaskHistoryItem` (`ClineProvider.ts:2231`, private)                                                                  | Returns the cached reference to the mode and profile updates, which spread before writing | No (shared reference) |
| `ClineProvider.getTaskWithId`                                                                                                          | Returns the cached reference onward to its own callers (which spread before writing)      | No (shared reference) |
| `Task.clearPendingActionAfterDurableResult`                                                                                            | Assigns the nested `pendingAction` object to an in-memory field                           | No                    |
| `Task.saveClineMessages`                                                                                                               | Reads `status` to preserve it in the rebuilt item                                         | No                    |
| `extension/api.ts` `getTaskHistoryItem`                                                                                                | Returns `structuredClone(item)`, so it is already defensive                               | No                    |
| `extension/api.ts` `TaskCompleted` listener                                                                                            | Reads `parentTaskId`                                                                      | No                    |
| Test suites (`TaskHistoryStore.*.spec.ts`, provider and delegation specs)                                                              | Read-only assertions, setup upserts, or stubbed mocks                                     | No                    |

`getByWorkspace` has no production callers (only a `TaskHistoryStore.spec.ts` suite exercises it); `packages/` and `apps/` contain no `TaskHistoryStore` usage. No current caller, production or test, mutates a returned record. The risk is latent: the API hands out live references, so any future or unspotted mutator bypasses the store lock entirely.

**Immutable read semantics (a recommendation for the implementation PR).** Records must leave the store as immutable snapshots. Evaluate in the implementation PR, in order of preference: (a) clone each record when it enters the cache, including the first insert, then deep-freeze the clone and return the frozen reference. Freezing the incoming object itself would freeze the caller's own argument. This option has no per-read cost and turns a mutation into a strict-mode `TypeError`. (b) `structuredClone` on read, which gives the strongest isolation but adds a per-read cost on the hot `getStateToPostToWebview` path. (c) type-level `ReadonlyDeep` plus lint, which gives no runtime safety and is the weakest. Option (a) with (c)'s types is the recommended combination given the all-read-only inventory.

**Clone/freeze test criteria (store tests).** A focused `TaskHistoryStore` test must obtain a record via `get`/`getAll`, attempt to mutate a scalar field and the nested `childIds` array, and assert that a second `get` and a subsequent `reconcile` from disk both show the unmutated record; under the freeze option the mutation attempt must throw in strict mode (or no-op) with the record unchanged. Compatibility exclusions recorded: webview/IPC serialization is unaffected; the `onWrite` array contract is unaffected; `getByWorkspace` may be removed or receive identical semantics; no test-suite rewrites beyond the new mutation-regression test are anticipated.

**Model/checker change.** Not applicable: this is a read-side API contract, not a transition protocol, and no faithful model boundary exists for object-reference mutability in the explicit-state explorers. The evidence is the caller inventory above plus the specified mutation-regression test.

## LIFE-BLK-P1-020 — stale-cache and convergence histories (GAP-020)

**Bounded property.** Watch/reconcile convergence is eventual and failure-tolerant, not coherent. For any finite, quiescing sequence of peer writes, a host whose next `reconcile()` completes with no per-task read error converges its cache to disk for every task ID. `reconcile()` catches per-task read errors and falls back to the lock-file check, so a reconcile that returns without an error does not prove that every entry converged. During the stale window there is no coherence guarantee. At the `mergeHistoryDelta` boundary (`taskStoreConcurrency.ts`), a same-field conflict resolves per field:

- `status`: a change that is not in `VALID_TASK_STATUS_TRANSITIONS` from the disk status throws `DeltaRejectedError`, and the whole delta is rejected. A legal change is applied.
- `childIds`: the delta is unioned with the disk value, so concurrent additions are all kept.
- Every other field: the delta value replaces the disk value (last writer wins).

The convergence property and its tests must cover these three cases separately. A rejected stale `status` write must leave the disk record unchanged. Concurrent `childIds` additions from two hosts must both survive. Exclusions: repeated reconcile failure (no convergence bound), network filesystems, process crash/power loss mid-write (`LIFE-BLK-P2-004`), and lock-implementation semantics.

**Observable histories (named, bounded).**

1. **Watcher-refresh history.** `fs.watch` watches the tasks directory without recursion (`TaskHistoryStore.ts:906`). It reports task directories that are created or deleted. It does not report an update to an existing `tasks/<id>/history_item.json`. Each event restarts a 500 ms debounce, so `reconcile()` runs 500 ms after the last event of a quiet period. Under a constant stream of events, the window has no fixed bound. A peer update to an existing record follows the missed-watch history.
2. **Missed-watch history.** Every peer update to an existing record takes this path. So does any `fs.watch` error or platform unreliability (handled in `startWatcher`, which logs and falls back). No event arrives, and the cache stays stale until the periodic reconcile (`RECONCILE_INTERVAL_MS`, 5 minutes) or an explicit refresh. Stale-read window bound: one periodic interval plus one reconcile pass, when reconciles succeed.
3. **Explicit-refresh history.** `invalidate(taskId)` re-reads one entry inside one store-lock acquisition. `delegateParentAndOpenChild` and the `reopenParentFromDelegation` continuation use it before they read authoritative state. The webview path runs `invalidateAll()` and then `reconcile()` (`webviewMessageHandler`), which takes two lock acquisitions, and `get()` returns `undefined` between them. In both cases the entry is fresh only as of the read instant. A peer write after the read starts a new stale window.

**Pending actions.** `reconcile()` and the repair paths do not change `pendingAction`. A reconcile keeps the value on disk, because it reads the record as written. Today settlement happens only through the settlement write at `ClineProvider.ts:752-757`. The open PR #1726 adds a disk-authoritative compare-and-clear. The stale-read window includes that settlement write. After an authoritative rejection, another host can still read the unsettled action until its next successful reconcile or `invalidate`. That host must not replay the action without the compare-and-clear.

`reconcile()` skips a cached task when the observed `mtimeMs` equals the recorded `taskFileMtimes` value (`TaskHistoryStore.ts:343-347`). This skip is not exact. A peer can replace `history_item.json` atomically while the filesystem reports the same `mtimeMs` for both writes, for example on a filesystem with coarse timestamps or with two writes in the same millisecond. `stat` succeeds in that case, so the lock-file liveness fallback does not run, and the cache keeps the stale payload. The convergence property above therefore holds only when each peer write changes the observed `mtimeMs`, or when a forced refresh runs (`invalidate`, `invalidateAll`, or `reconcile({ forceRefresh: true })`).

The implementation PR must close this gap with a stronger change marker. `safeWriteJson` writes a new temporary file and renames it into place, so each write creates a new inode. Record `ino` and `size` with `mtimeMs`, and skip the read only when all three match. On a platform that does not report a stable `ino`, fall back to a forced read. The lock-file liveness fallback still keeps a task live across a peer's atomic rename window instead of evicting it.

**Objective convergence evidence (existing).** `TaskHistoryStore.crossInstance.spec.ts` covers peer create/delete/update detection through reconciliation and invalidation visibility with two real stores; `TaskHistoryStore.realConcurrency.spec.ts` exercises the real `proper-lockfile` plus rename path; `TaskHistoryStore.reconciliation.spec.ts` covers drift repair. These are focused production tests, not exhaustive interleavings.

**Additional test evidence required for closure (deterministic, no timing sleeps).**

- _Missed-watch:_ construct a store whose watcher is stubbed to error or never fire, commit a peer write through a second real store, advance fake timers past the periodic interval (or invoke `reconcile()` directly), and assert byte-level convergence with disk.
- _Missed-watch with concurrent update:_ during the stale window, perform a local delta write and assert the peer's fields survive (delta merge preserves fields absent from the delta), then assert convergence after the next successful reconcile.
- _Same-mtime replace:_ commit a peer write, then set the file's `mtime` back to the recorded value with `fs.utimes`. Assert that the next `reconcile()` reads the new payload. This test fails today and passes with the stronger change marker.
- _Reconcile-failure injection:_ inject a reconcile failure inside the window and assert only that the stale window extends — never that state diverges — with a successful reconcile restoring convergence. Rollback verification: after each injected failure, the cache must equal either the pre-write or post-write disk state, never a partial merge.

**Shared-store landmarks.** The existing `stale-cache-newer-disk` semantic landmark already requires a reachable state where a host cache diverges from newer disk state; this block names the histories that produce and resolve it. No checker change in this PR: the watcher, debounce, and timers are environment effects, and the explicit-state explorer models `refresh` as an environment action already; a timing-faithful watcher model would require the temporal semantics the suite deliberately defers (see the lifecycle model page's tooling rationale). Depends on the LIFE-BLK-P1-001 vocabulary — satisfied within this document.

## LIFE-BLK-P1-039 — continuation of a completed task (GAP-039)

**Status.** Open. This document does not specify it yet.

**Gap.** A user can continue a completed task (`resume_completed_task`, `Task.ts:2406-2424`), but `completed` has no outgoing transition in `VALID_TASK_STATUS_TRANSITIONS`. The continued task keeps the stored status `completed`, and a later delegation from it fails the `completed → delegated` check (`taskLifecycle.ts:47`).

**Open decision.** The product requirement PR-4 in the target architecture leaves one choice open: add a `completed → active` transition, or move the continued work to a linked successor task. The specification follows that decision.

A `completed → active` transition breaks two existing guarantees, so that option must replace them: model invariant 6, "Completed task records cannot be changed by later lifecycle events" (`task-lifecycle-model.md`, Invariants), and the checker's terminal checks (`check-task-lifecycle.ts:143-147, 188-189`). The linked-task option keeps both.
