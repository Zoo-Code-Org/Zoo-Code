## 1. ФУНДАМЕНТАЛЬНЫЕ ПРИНЦИПЫ

### 1.1 Никаких предположений

**Никогда** не предполагай. Любое «наверное», «может быть», «скорее всего» — красный флаг. Каждое утверждение должно быть проверено:

- Прочитан код (конкретные файлы и строки)
- Подтверждено через MCP (Context7 для API/библиотек, Tavily для практик)
- Верифицировано тестами

**Цитата:** _«У тебя не должно оставаться вообще никаких вопросов, а только конкретная идеальная реализация, выверенная до микрона»_

### 1.2 Сначала пойми корень, потом правь

Не пиши код, пока не поймёшь **почему** проблема возникла.

- Симптом → гипотеза → верификация через код и MCP → корень → фикс
- Если не уверен в корне — делай ещё один раунд исследования

**Провал:** В первой сессии CRT начали писать код, не поняв, что strict mode ломает всё. Получили 19 файлов изменений, которые не работали.

### 1.3 Каждое движение должно быть выверено

Прежде чем применить изменение:

1. Прочитай файл
2. Проверь через MCP best practices
3. Напиши точный diff
4. Проверь TypeScript
5. Запусти тесты

### 1.4 Используй все доступные инструменты

Перед каждым действием спрашивай себя:

- **Скиллы:** Подходит ли какой-то из доступных скиллов? (`joko-orchestrator`, `angular-architect`, `typescript-pro`, `node-specialist`, `evals-context`, `roo-conflict-resolution`, `roo-translation`, `mcp-builder`, `defuddle`, `python-pro`, `golang-pro`, `rust-engineer`, `react-specialist`, `nextjs-developer`, `vue-expert`, `flutter-expert`, `sql-pro`, `fastapi-developer`, `django-developer`, `laravel-specialist`, `symfony-specialist`, `spring-boot-engineer`, `csharp-developer`, `dotnet-core-expert`, `cpp-pro`, `java-architect`, `kotlin-specialist`, `elixir-expert`, `rails-expert`, `swift-expert`, `expo-react-native-expert`, `php-pro`, `powershell-7-expert`, `javascript-pro`, `keyboard-layout-decoder`)
- **MCP:** Нужно ли проверить API/библиотеку через Context7? Нужен ли поиск через Tavily?
- **Поиск по кодовой базе:** `search_files` с regex может найти то, что не заметишь глазами

Загружай скилл перед каждым действием, где он может быть полезен. Даже если скилл помогает на 10% — используй его.

## 2. ПРОЦЕСС РАБОТЫ

### 2.1 Фаза 0: Глубокое исследование (самая важная)

Не пропускай этот этап. Никогда.

```
Wave 1: Аудит кода
  → прочитать все релевантные файлы
  → зафиксировать текущее состояние (строки, типы, логику)
  → создать отчёт с точными номерами строк

Wave 2: MCP исследование
  → Context7: resolve-library-id + query-docs для каждой библиотеки/API
  → Tavily: поиск best practices, известных проблем, issue
  → создать отчёт с цитатами источников

Wave 3: Верификация
  → проверить каждое утверждение из Wave 1+2 в реальном коде
  → создать VERIFICATION файл с точными строками

Wave 4: Синтез
  → объединить всё в единый план правок
  → две версии: План A (идеал) и План B (минимальные правки)
```

**Успех:** После 6 волн исследования нашли 3 корневые проблемы и исправили их 4 минимальными правками.

### 2.2 Фаза 1: Планирование

Перед тем как делегировать:

1. **Interview самого себя:** Что именно нужно сделать? Какие границы? Как проверить?
2. **Разбей на независимые задачи:** Что можно делать параллельно?
3. **Определи зависимости:** B.2 зависит от B.1? chat.ts можно делать параллельно с base-provider.ts?
4. **Напиши acceptance criteria:** Как узнать, что задача сделана?

### 2.3 Фаза 2: Делегирование агентам

**Правило 1: Полный контекст**
Каждому агенту давай:

- Что сделать (точное описание)
- Почему (какую проблему решает)
- Как проверить (acceptance criteria)
- Ссылки на файлы (относительные пути)
- Запрет на сокращение вывода

**Правило 2: Запрет на truncation вывода**
ВСЕГДА добавляй в инструкцию агенту:

```
КРИТИЧЕСКИ ВАЖНО: Все команды запускай с ПОЛНЫМ выводом.
НЕ ИСПОЛЬЗУЙ tail, head или другие обрезатели.
Для длинного вывода используй перенаправление в файл:
  command > /tmp/agent-output-xxx.txt 2>&1
  # потом прочитай файл через read_file или read_command_output
```

Без этого агенты получают обрезанный вывод и делают неверные выводы.

**Правило 3: Один агент — одна задача**
Не нагружай одного агента всем сразу. Лучше 5 простых задач, чем 1 сложная.

**Правило 4: Сохраняй скепсис**
Никогда не верь агенту на слово. Всегда проверяй его результат:

- Прочитай изменённые файлы
- Запусти тесты
- Если есть сомнения — запусти критика

### 2.4 Фаза 3: Агент-критик

**Запускай критика ПОСЛЕ КАЖДОЙ правки.**

Критик должен:

1. Прочитать изменённые файлы
2. Проверить каждое утверждение через MCP
3. Найти проблемы, которые пропустил исполнитель
4. Выдать вердикт: ✅ / ⚠️ / ❌

**Цитата:** _«Выбери самый подходящий режим и периодически запускай агента критика, который будет придирчиво осматривать все и выводить тебе критические отчеты»_

**Реальный кейс:** Критик нашёл, что `openai-native.ts` имеет свою копию `ensureAllRequired()`, которую мы забыли синхронизировать. И что `strict: true` остался в двух source-файлах.

## 3. ТЕХНИЧЕСКИЕ ПАТТЕРНЫ

### 3.1 Strict mode и tool schemas

**Золотое правило:** Если параметр может быть опущен — он НЕ должен быть в `required`, даже если strict mode «просит». Strict mode применяется runtime-провайдерами, не source-схемами.

**Для OpenAI:** `convertToolSchemaForOpenAI()` перезаписывает `required = allKeys` и удаляет `null` из `type`. Это ломает optional параметры.

**Фикс:** Сохраняй оригинальный `required`, не удаляй `null` из union-типов.

### 3.2 Архитектура контекстных данных

В AI-агентах есть три слоя данных:

| Слой | Где                        | Живёт         | Для чего             |
| ---- | -------------------------- | ------------- | -------------------- |
| 0    | `assistantMessageContent`  | 1 стрим       | Только текущий ответ |
| 1    | `apiConversationHistory`   | Вся сессия    | Полная история       |
| 2    | `getEffectiveApiHistory()` | Active window | Что видит API        |

**Критическое:** Никогда не используй Layer 0 для цитирования — он пуст после стрима.

### 3.3 Обработка ошибок в tool call'ах

Всегда добавляй **graceful fallback**:

- Если `ref` не сработал → используй оригинальный параметр
- Модель не должна узнать об ошибке
- Логирование в `console.error`, не в user message

[Пошагово, конкретно]

[Список с путями]

[Acceptance criteria]

- Используй `apply_diff` для изменений
- English-only comments
- ВСЕГДА полный вывод команд (не обрезай)
- Для длинного вывода: команда > /tmp/xxx.txt 2>&1
- Если сомневаешься — используй MCP (Context7, Tavily)

### 4.2 Реагирование на прерывания

**Баг:** Если пользователь пишет сообщение под-агенту, `askApproval` в `presentAssistantMessage.ts:508` интерпретирует это как отказ.

**Митигация:** Пока нет фикса — избегай ситуаций, где пользователь может вмешаться в работу агента.

### 5.1 Что должно быть в каждом отчёте

1. **Executive Summary** (5-10 строк)

- Финальные отчёты → в корень `OTCHETY/`
- Черновики/промежуточные → `OTCHETY/old/`
