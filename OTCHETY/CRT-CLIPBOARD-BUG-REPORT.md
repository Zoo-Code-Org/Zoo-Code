## 1. Краткое резюме

Universal AI Clipboard (CRT v5.0) — механизм zero-token copy-paste, описанный в системном промпте. Из **12 задокументированных возможностей** фактически работает **только одна**: `source=file` + `selector` — и то с ограничением (возвращает только точную совпавшую строку, а не AST-блок).

**Ключевые провалы:**

- **AST-авторасширение (`focus`)** — не работает. Вместо целого синтаксического блока возвращает 15-23 символа (первое текстовое совпадение)
- **`source=chat`** — полностью не работает. `[CRT] ref not found`
- **`multi_ref`** — полностью не работает
- **Inline-инъекция `{{ref:...}}`** — полностью не работает. Записывается как литерал
- **`apply_diff` с `ref` без `diff`** — не работает. Требуется валидный SEARCH/REPLACE формат

## 4. Детальный анализ багов

### 🐛 БАГ #1 (КРИТИЧЕСКИЙ): AST-авторасширение не работает

**Симптом:** `focus` возвращает только первое текстовое совпадение вместо всего синтаксического блока

**Лог:**

```
[SUCCESS] Resolved ref. Content length: 23
[EXECUTE] with resolved params: {"content":"countTokensResultSchema"}
```

**Ожидалось:** `content` должен содержать всю функцию (46 строк, ~800 символов)

**Корень проблемы:** Параметр `focus` не подключён к tree-sitter AST-парсеру (который существует в кодовой базе — см. `src/services/tree-sitter/`). Вместо этого он работает как примитивный текстовый поиск `find()` по содержимому файла.

**Доказательство:** В логе указано `method=exact` — это метод точного текстового совпадения, а не `method=ast`.

---

### 🐛 БАГ #2 (КРИТИЧЕСКИЙ): source=chat полностью не работает

**Симптом:** Любые попытки прочитать данные из чата возвращают ошибку

**Лог:**

```
[ERROR] Failed to resolve ref: Could not find quote in source "chat:-1"
[CRT] ref not found: source=chat:-1, selector="## Результаты полного тестирования"
— resolution failed, falling back to original params
```

**Возможные причины:**

1. История чата хранится в формате, недоступном для CRT-резолвера (например, сжатом/закодированном)
2. Механизм поиска по чату использует потоковый контекст, который уже GC-собран между вызовами
3. Параметр `ref="-1"` интерпретируется как файл с именем `-1`, а не как индекс сообщения

**Дополнительная проблема:** После первой ошибки `source=chat` система не оставляет trace в логе для последующих вызовов (тесты 7, 8) — тихий сбой без логирования.

---

### 🐛 БАГ #3 (КРИТИЧЕСКИЙ): multi_ref не работает

**Симптом:** Файл остаётся пустым после вызова с `multi_ref`

**Лог:** Нет записи вообще

**Причина:** Параметр `multi_ref`, вероятно, не имплементирован в текущей сборке runtime, хотя описан в системном промпте.

---

### 🐛 БАГ #4 (СРЕДНИЙ): Inline-инъекция {{ref:...}} не работает

**Симптом:** Синтаксис `{{ref:...}}` записывается как литеральный текст во всех инструментах

**Лог:** Нет записи о попытке резолвинга

**Причина:** Препроцессор строк, который должен распознавать `{{ref:...}}` и заменять на содержимое, отсутствует или отключён.

---

### 🐛 БАГ #5 (СРЕДНИЙ): apply_diff с ref без diff приводит к ошибке

**Симптом:** CRT резолвит `ref` и подставляет его в `diff`, но `apply_diff` требует валидный SEARCH/REPLACE формат

**Лог:**

```
[SUCCESS] Resolved ref. Content length: 23
[EXECUTE] with resolved params: {"diff":"countTokensResultSchema"}
```

→ Ошибка: `Invalid diff format - missing required sections`

**Причина:** Согласно инструкции «When using ref, omit the primary text parameter (e.g. diff)», я опустил `diff`. Но `apply_diff` **обязательно требует** валидный `diff`-формат. `ref` подставляет содержимое в `diff`, но не форматирует его как SEARCH/REPLACE.

---

### 🐛 БАГ #6 (НИЗКИЙ): startAnchor/endAnchor не работают

**Симптом:** Вызов с `startAnchor` и `endAnchor` не даёт результата, файл пуст

**Лог:** Нет записи

**Причина:** Вероятно, механизм Anchor Pair требует `contextType` для правильной работы, либо не имплементирован.

## 5. Анализ лога системы

### 5.1 Структура лога

Лог `crt-debug.log` фиксирует три этапа:

```
[TIMESTAMP] [CALL] Tool "xxx" initiated. block.refMeta={...}
[TIMESTAMP] [SUCCESS|ERROR] Resolved ref. details...
[TIMESTAMP] [EXECUTE] Executing "xxx" with resolved params: {...}
```

### 5.2 Выдержка из лога

```
#1 [12:18:31] [CALL] write_to_file. refMeta={"ref":{source:"file", ref:"countTokens.ts", focus:"countTokens"}}
#1 [12:18:31] [SUCCESS] Resolved ref. source=file:countTokens.ts, method=exact, confidence=0.95. Content length: 23
#1 [12:18:31] [EXECUTE] content: "countTokensResultSchema"

#2 [12:20:20] [CALL] write_to_file. refMeta={"ref":{source:"chat", ref:"-1", selector:"## Результаты полного тестирования"}}
#2 [12:20:20] [ERROR] Failed to resolve ref: Could not find quote in source "chat:-1"
#2 [12:20:20] [EXECUTE] content: "" (empty fallback)
```

### 5.3 Ключевые наблюдения из лога

1. **`method=exact`** — метод всегда `exact`, что подтверждает текстовый (не AST) поиск
2. **`confidence=0.95-1.00`** — высокая уверенность, но это confidence текстового совпадения, не AST
3. **`Content length`** — всегда мал (15-28 символов), что доказывает отсутствие AST-расширения
4. **Fallback работает** — при ошибке используется оригинальный параметр (пустая строка)
5. **Нет дифференциации ошибок** — `ERROR` не содержит информации о том, какой этап поиска не сработал

## 6. Когнитивный анализ: почему агент допускал ошибки

### 6.1 Документация вводит в заблуждение

Системный промпт описывает Clipboard так, как будто **все функции уже работают**:

- «focus — AST-парсер автоматически найдёт слово и расширит выделение до всего содержащего синтаксического блока»
- «multi_ref — позволяет собрать содержимое из нескольких источников за один вызов»
- «inline-инъекция — система автоматически разрешит ссылку»
- «ref — опускайте primary text parameter»

Но ни одна из этих функций **не реализована**. Это создаёт ложное представление о возможностях инструмента.

### 6.2 Конфликт инструкций

Правило **«omit the primary text parameter»** вступает в противоречие с требованиями инструментов:

| Инструкция                     | Реальность                             |
| ------------------------------ | -------------------------------------- |
| «When using ref, omit content» | `write_to_file` работает без `content` |
| «When using ref, omit diff»    | `apply_diff` **требует** diff-формат   |
| «When using ref, omit command» | Не тестировалось (shell command)       |

Для `apply_diff` это буквально **невозможно выполнить** — diff-формат обязателен.

### 6.3 Скрытое поведение (silent failures)

Некоторые режимы (`startAnchor/endAnchor`, `multi_ref`, `source=chat` после первой ошибки) **тихо проваливаются** без записи в лог. Агент не получает обратной связи, что вызов не сработал.

### 6.4 Почему я потратил 15+ вызовов на тестирование?

1. **Первые 5 вызовов** — я не знал, что `ref` нужно передавать как отдельный JSON-параметр (думал, inline `{{ref:...}}` сработает)
2. **Следующие 3 вызова** — я передавал `content` вместе с `ref`, что блокировало резолвинг
3. **Следующие 3 вызова** — я тестировал `apply_diff`, не понимая что diff-формат обязателен
4. **Последние 4 вызова** — я пытался понять почему `source=chat` не работает

**Проблема:** В документации нет:

- Чёткого разделения между inline-инъекцией и нативным `ref`
- Спецификации формата для каждого инструмента
- Примеров успешного и неуспешного использования

### 6.5 Типичные ошибки оператора

| Ошибка                                                  | Причина                                 | Частота |
| ------------------------------------------------------- | --------------------------------------- | :-----: |
| Использование `{{ref:...}}` вместо нативного JSON `ref` | Путаница между inline и native режимами | ⭐⭐⭐  |
| Передача `content` вместе с `ref`                       | Привычка к стандартному API             |  ⭐⭐   |
| Ожидание AST-расширения от `focus`                      | Буквальное прочтение документации       | ⭐⭐⭐  |
| Ожидание работы `source=chat`                           | Буквальное прочтение документации       |  ⭐⭐   |
| Попытка `ref` без `diff` в `apply_diff`                 | Буквальное выполнение инструкции        |  ⭐⭐   |

## 7. Проблемы проектирования API

### 7.1 Два синтаксиса для одного механизма

Существует **два способа** использовать Clipboard:

1. **JSON-параметр `ref`** внутри вызова инструмента (нативный)
2. **Inline `{{ref:source=...,ref=...}}`** внутри строковых параметров

Проблема: они **выглядят одинаково**, но **работают по-разному**. Inline-инъекция не работает вообще, нативный `ref` работает с ограничениями.

### 7.2 Неоднозначность `focus`

Параметр `focus` обещает AST-расширение, но реализован как текстовая подстрока. Нет индикации в API:

- `method=exact` vs `method=ast` — различие должно быть явным
- `confidence` — неясно что он означает для текстового поиска

### 7.3 Отсутствие спецификации для `source`

| source     | Документирован? | Работает? | Формат ref                    |
| ---------- | :-------------: | :-------: | ----------------------------- |
| `chat`     |       ✅        |    ❌     | Индекс сообщения (`-1`, `-2`) |
| `file`     |       ✅        |    ⚠️     | Путь к файлу                  |
| `terminal` |       ✅        |    ❓     | Имя артефакта                 |
| `tool`     |       ✅        |    ❓     | Имя инструмента               |

Нет спецификации:

- Какой формат у каждого `ref`?
- Как проверить, что источник доступен?
- Какие есть fallback-стратегии?

### 7.4 Нет обратной связи при неудаче

Успешный резолвинг: `[CRT] ref resolved: ... Content length: N`
Неуспешный: `[CRT] ref not found: ... — resolution failed`
Тихий сбой: (ничего)

Нет:

- Причины неудачи (файл не найден, AST не распарсен, чат недоступен)
- Предложения исправления (попробуйте selector вместо focus)
- Статистики (сколько блоков найдено, какой процент покрытия)

## 8. Рекомендации по исправлению

### 8.1 Немедленные (quick wins)

| Баг                              | Исправление                                                     | Сложность |
| -------------------------------- | --------------------------------------------------------------- | :-------: |
| Inline `{{ref:...}}` не работает | Добавить препроцессор строк в runtime перед вызовом инструмента |  Средняя  |
| `source=chat`                    | Исправить резолвер для доступа к conversation history           |  Высокая  |
| `multi_ref`                      | Добавить поддержку массива ref-объектов                         |  Средняя  |
| Лог для тихих сбоев              | Добавить запись в лог для всех случаев отказа                   |  Низкая   |

### 8.2 Среднесрочные

1. **Подключить tree-sitter AST** к `focus`-режиму

    - В кодовой базе уже есть `src/services/tree-sitter/`
    - `focus` должен использовать `parseSourceCodeDefinitions()` для поиска блока
    - Если AST-парсер не может распарсить файл — fallback на текстовый поиск

2. **Уточнить контракт `apply_diff` с `ref`**

    - `ref` в `apply_diff` должен подставлять **только REPLACE-часть**
    - SEARCH-часть должна быть явной или авто-генерироваться
    - Либо добавить новый инструмент `replace_block` для случая «найти блок и заменить»

3. **Добавить валидацию параметров**
    - Если `source=chat` и `ref` не в формате числа — ошибка на этапе валидации
    - Если `focus` не найден в файле — понятное сообщение

### 8.3 Долгосрочные

1. **Единый API для clipboard**

    - Убрать дублирование inline/native
    - Оставить только нативный JSON-параметр `ref`
    - Inline-синтаксис (`{{ref:...}}`) переделать в MCP resource URI

2. **Система обратной связи**

    - `[CRT] summary` — после каждого вызова показывать таблицу с ref-статистикой
    - Подсветка в IDE: показать какой блок будет скопирован до выполнения

3. **Graceful degradation**
    - Если AST не сработал → попробовать текстовый поиск
    - Если selector не нашёл → попробовать fuzzy match
    - Если chat недоступен → fallback на file (сохранять чат в файл)

## 9. Предложения по редизайну

### 9.1 Новая архитектура CRT Clipboard v6.0

```
[Агент] → ref-запрос
                ↓
[CRT Router]
    ├─ source=file?    → FileResolver
    │   ├─ focus?      → ASTResolver (tree-sitter) → fallback → TextResolver
    │   ├─ selector?   → TextResolver
    │   └─ anchor?     → RangeResolver
    ├─ source=chat?    → ChatResolver (conversation API)
    ├─ source=terminal?→ ArtifactResolver
    └─ source=tool?    → ToolResultResolver
                ↓
[PostProcessor]
    ├─ transform.pipeline (replace/prepend/append/wrap/join)
    └─ format-adapter (подготовка к конкретному инструменту)
                ↓
[Инструмент] → исполнение с подставленными данными
```

### 9.2 Новый формат запроса

```json
{
  "ref": {
    "sources": [
      { "type": "file", "path": "src/utils/safeWriteJson.ts", "mode": "ast", "focus": "safeWriteJson" },
      { "type": "file", "path": "src/utils/countTokens.ts", "mode": "text", "selector": "export async function" }
    ],
    "strategy": "merge" | "replace" | "first-match",
    "fallback": "warn" | "fail" | "skip",
    "transform": {
      "join_with": "\n\n",
      "wrap": "// region\n$CONTENT\n// endregion"
    }
  }
}
```

### 9.3 Унификация инструментов

Вместо того чтобы каждый инструмент по-своему обрабатывал `ref`, добавить **единый middleware-слой**:

```
Tool Call → CRT Middleware → Resolve ref → Transform → Validate → Execute
```

Это гарантирует:

- Единое поведение для всех инструментов
- Централизованное логирование
- Консистентную обработку ошибок

### 9.4 Формат обратной связи

Успех:

```
[CRT] source=file → safeWriteJson.ts
      mode=ast → "safeWriteJson" (function, 159 lines, confidence=0.97)
      transform: replace(console.error→logger.error)
      result: 159 lines → 159 lines (1 replacement)
```

Ошибка:

```
[CRT] source=chat → ref=-1, mode=ast, focus="myFunction"
      ✗ ERROR: Chat history source "-1" not available
      └─ Reason: conversation buffer GC-collected (age: 15min)
      └─ Suggestion: use source=file with explicit path, or save chat to file first
```

## 10. Заключение

### Текущее состояние

Universal AI Clipboard (CRT v5.0) — это **недостроенный механизм**. Из всей мощной функциональности, описанной в системном промпте, реально работает только `source=file` + `selector` (и то как примитивный текстовый поиск). AST-расширение, multi-ref, source=chat, inline-инъекция — **не функционируют**.

### Корневая причина

Проблема не в отдельных багах, а в **разрыве между документацией и реализацией**. Системный промпт описывает **целевую архитектуру** (vision), но runtime реализует лишь **10-20% от заявленного**. Это приводит к:

- Потере времени агента на тестирование неработающих функций
- Ложным ожиданиям
- Тихим сбоям без обратной связи

### Главные рекомендации

1. **Привести документацию в соответствие с реализацией** — временно убрать упоминания неработающих функций
2. **Добавить логирование для всех тихих сбоев**
3. **Подключить существующий tree-sitter AST-парсер** к `focus`-режиму
4. **Переработать API** в единый middleware-слой с чёткими контрактами
5. **Добавить обратную связь** — агент должен видеть, что скопировано и сколько

### Метрики

| Показатель                     |            Значение            |
| ------------------------------ | :----------------------------: |
| Задокументировано возможностей |              ~12               |
| Фактически работает            |    1 (source=file+selector)    |
| Работает с ограничениями       | 1 (source=file+focus, без AST) |
| Не работает                    |              ~10               |
| Процент успешной реализации    |             ~8-16%             |
