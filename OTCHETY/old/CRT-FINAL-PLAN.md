## 1. Executive Summary

CRT-модуль (Content Reference Tool) имеет **2 критические архитектурные проблемы** и **1 operational issue**:

1. **OpenAI strict mode конвертирует `type: ["object", "null"]` → `type: "object"`** для `ref`/`multi_ref`/`transform`, лишая модель возможности НЕ передавать эти параметры. Это добавляет ~200-300 токенов на каждый tool call. Модель «знает» цену и игнорирует `ref` полностью.
2. **`chat.ts` читает из `assistantMessageContent` (Layer 0 — стрим-буфер одного сообщения)**, а должен читать из `getEffectiveApiHistory()` (Layer 2 — effective history, то, что реально видит API). Из-за этого `"-1"` работает только во время текущего стрима, а `"-2"`, `"-3"` и т.д. никогда не работают.
3. **`ref`/`multi_ref`/`transform` находятся в корневом `required` массиве** всех 7 tool schema, что в strict mode делает их генерацию принудительной.

**Ключевой вывод:** CRT не будет работать корректно, пока не исправлены обе архитектурные проблемы — и передача `ref` через tool parameters, и источник данных для `source:chat`.

## 2. Критические проблемы (в порядке приоритета)

### Проблема A: OpenAI strict mode + CRT-параметры (БЛОКИРУЮЩАЯ)

| Аспект                   | Значение                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Что именно не так**    | `convertToolSchemaForOpenAI()` в [`base-provider.ts:87-89`](src/api/providers/base-provider.ts:87) удаляет `null` из union-типов. `type: ["object", "null"]` → `type: "object"`. Все CRT-параметры становятся required, non-nullable.                                                                                                                                                                     |
| **Почему блокирует CRT** | Модель **обязана** генерировать полный объект `ref` (со всеми 6 nested required полями) при каждом вызове любого из 7 инструментов. Это ~200-300 токенов накладных расходов. На практике модель просто игнорирует `ref`.                                                                                                                                                                                  |
| **Где в коде**           | [`src/api/providers/base-provider.ts:63-106`](src/api/providers/base-provider.ts:63) — вся функция `convertToolSchemaForOpenAI()`, особенно строки 79 (`result.required = allKeys`) и 87-89 (удаление null).                                                                                                                                                                                              |
| **Варианты решения**     | **A1** (рекомендуемый): Экранировать CRT-параметры от strict mode — не добавлять их в `required`, сохранять `null` в union. **A2** (радикальный): Вынести `ref`/`multi_ref`/`transform` из tool schemas полностью в отдельный metadata-канал. **A3** (минимальный): Убрать `ref` из `required` на уровне исходных схем — НО это не сработает для OpenAI strict mode (strict игнорирует не-required поля). |

### Проблема B: chat.ts читает из стрим-буфера (БЛОКИРУЮЩАЯ)

| Аспект                   | Значение                                                                                                                                                                                                                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Что именно не так**    | [`chat.ts:28`](src/core/tools/ref/sources/chat.ts:28) читает `task.assistantMessageContent` — это Layer 0 (стрим-буфер). Он содержит блоки **только текущего стримящегося сообщения** и очищается при старте каждого нового API-запроса ([`Task.ts:2615`](src/core/task/Task.ts:2615)). |
| **Почему блокирует CRT** | `"-1"` работает только во время активного стрима. После завершения стрима массив пуст → `"-1"` out of bounds. `"-2"`, `"-3"` и т.д. **никогда не работают**, потому что массив всегда содержит 0-N блоков одного (текущего) сообщения.                                                  |
| **Где в коде**           | [`src/core/tools/ref/sources/chat.ts:28`](src/core/tools/ref/sources/chat.ts:28) — строчка `const messages = task.assistantMessageContent`.                                                                                                                                             |
| **Варианты решения**     | **B1** (рекомендуемый): Переключиться на `getEffectiveApiHistory(task.apiConversationHistory)` (Layer 2 — то, что видит API). **B2** (альтернатива): Читать из `task.apiConversationHistory` напрямую (Layer 1 — все сообщения). B1 предпочтительнее для консистентности с LLM.         |

### Проблема C: CRT-параметры в required массиве (УСУГУБЛЯЮЩАЯ)

| Аспект                | Значение                                                                                                                                                                                                                                                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Что именно не так** | Во всех 7 tool schema файлах `ref`/`multi_ref`/`transform` перечислены в корневом `required` массиве. Для strict mode это означает, что модель **обязана** сгенерировать все три параметра каждый раз.                                                                                                                                            |
| **Почему усугубляет** | Даже если починить конвертер (Проблема A), `required` + nested required поля (у `ref` — 6 полей, у `transform` — 5 полей) создают «максимально строгую» схему. Каждый optional nested параметр «удваивает грамматическое пространство» (Anthropic).                                                                                               |
| **Где в коде**        | 7 файлов: [`src/core/prompts/tools/native-tools/apply_diff.ts`](src/core/prompts/tools/native-tools/apply_diff.ts), `execute_command.ts`, `write_to_file.ts`, `search_replace.ts`, `edit_file.ts`, `edit.ts`, `apply_patch.ts`. Везде строка вида: `required: ["path", "diff", "ref", "multi_ref", "transform"]`.                                 |
| **Варианты решения**  | **C1** (рекомендуемый): Убрать `ref`/`multi_ref`/`transform` из корневого `required` массива во всех 7 файлах. **C2** (дополнительно): Убрать часть nested required полей в `ref.properties` (сделать `startAnchor`/`endAnchor`/`selector`/`contextType` опциональными). **C3**: Оставить как есть, но тогда Проблема A должна работать идеально. |

## 5. План A (идеальная архитектура) и План B (минимальные правки)

### План A: Идеальная архитектура (рекомендуется)

**Цель:** Полноценная система цитирования, устойчивая к strict mode, эффективная по токенам, консистентная для всех провайдеров.

| Шаг     | Что сделать                                                                                                                                                               | Затраты | Эффект                                                          |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- | --------------------------------------------------------------- |
| **A.1** | Убрать `ref`/`multi_ref`/`transform` из tool schemas полностью. Сделать их **мета-параметрами**, передаваемыми через metadata API-запроса (или post-processing инжекцию). | Высокие | Полное исключение токенных накладных расходов от CRT-параметров |
| **A.2** | Переключить `chat.ts` на `getEffectiveApiHistory()` (Layer 2).                                                                                                            | Средние | `"-1"`..`"-N"` работают для всех сообщений в active window      |
| **A.3** | Реализовать **Virtual Content Grid (VCG)** — индекс сообщений/блоков в active window. Подавать VCG в system prompt.                                                       | Высокие | Модель может точно цитировать любой контент по координатам      |
| **A.4** | Реализовать **server-side ref injection**: после получения tool call от модели, сервер автоматически добавляет ref на основе контекста (ретроспективное цитирование).     | Высокие | Модели не нужно генерировать ref вообще                         |
| **A.5** | Добавить **режим full-archive**: `source:"archive"` для цитирования сконденсированных сообщений.                                                                          | Средние | Полный доступ ко всей истории                                   |

**Итог:** Модель тратит 0 токенов на CRT. Все references восстанавливаются пост-фактум.

---

### План B: Минимальные правки (быстрый фикс)

**Цель:** Починить CRT настолько, чтобы он **работал базово** для большинства провайдеров, с минимальными изменениями.

| Шаг     | Что сделать                                                                                           | Затраты                         | Эффект                                                                                |
| ------- | ----------------------------------------------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------- |
| **B.1** | Убрать `ref`/`multi_ref`/`transform` из `required` в 7 tool schema файлах.                            | **Малая** (7 файлов × 1 строка) | Anthropic/Mistral/Ollama — модель может не передавать ref. Для OpenAI — не сработает. |
| **B.2** | Модифицировать `convertToolSchemaForOpenAI()` — экранировать CRT-параметры от strict mode (Правка 1). | **Средняя** (~30 строк)         | OpenAI strict mode перестаёт требовать CRT-параметры.                                 |
| **B.3** | Переключить `chat.ts` на Layer 2 (Правка 2).                                                          | **Средняя** (~50 строк)         | source:chat начинает работать для всех сообщений.                                     |
| **B.4** | Добавить инструкцию в system prompt про использование `ref`.                                          | **Малая** (~5 строк)            | Модель получает сигнал, что ref опционален.                                           |
| **B.5** | Аудит рантайм-обработки отсутствующих CRT-параметров (Правка 4).                                      | **Средняя**                     | Предотвращение crash при отсутствии ref.                                              |

**Итог:** CRT работает (модель МОЖЕТ генерировать ref, но не обязана). source:chat работает для всей истории.

## 6. Рекомендация

**Начать с Плана B** (минимальные правки). Это даст:

1. Работающий `source:chat` для всей истории сообщений (фикс chat.ts)
2. Существенное снижение токенных накладных расходов для всех провайдеров (optional ref)
3. Отсутствие регрессий для существующих провайдеров
4. Базу для дальнейшего улучшения до Плана A

План A (VCG + metadata-канал + post-processing) — это архитектура следующего поколения CRT, которую можно реализовать после стабилизации Плана B.

**Порядок выполнения Плана B:**

1. **Правка 3** (убрать CRT-параметры из required) — 7 файлов, 10 минут
2. **Правка 1** (экранировать CRT-параметры в base-provider.ts) — 30 минут + тестирование
3. **Правка 2** (переключить chat.ts на Layer 2) — 1 час + тестирование
4. **Правка 4** (аудит рантайма) — 1-2 часа
5. **Правка 5** (system prompt) — 15 минут
